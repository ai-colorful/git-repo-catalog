## 2. 项目是什么，解决什么问题

Clash Verge Rev 是原 zzzgydi/clash-verge 的延续项目（README.md 开头即注明 "Continuation of Clash Verge"），为 mihomo（原 Clash.Meta）内核提供图形化桌面外壳。用户导入机场订阅或本地 YAML 配置后，由 GUI 完成：配置管理与增强、系统代理/TUN 虚拟网卡接管、节点选择与测速、规则可视化编辑、WebDav 备份等。内核本身（mihomo，Go 编写）不在此仓库内，以 sidecar 二进制形式打包（src-tauri/tauri.conf.json 中 `externalBin: ["sidecar/verge-mihomo", "sidecar/verge-mihomo-alpha"]`），并通过 HTTP API（tauri-plugin-mihomo 插件）与 GUI 通信。

它解决的核心痛点是：mihomo 内核只有命令行与 REST API，普通用户需要一个能跨 Windows/macOS/Linux 处理"提权"问题的 GUI。这里最麻烦的是权限模型——设置系统代理需要写注册表/网络偏好，开启 TUN 需要管理员/root 权限，而 GUI 主程序不应长期以管理员运行。项目为此设计了独立的特权服务（clash-verge-service，独立仓库 clash-verge-service-ipc，Cargo.toml 中固定 tag v2.7.6）：内核由服务以高权限运行，GUI 降权运行；服务不可用时回退到 Sidecar 模式（内核随 GUI 进程启动、牺牲 TUN）。

功能面在 README.md 中列出：Rust + Tauri 2、内置 mihomo 内核并可切换 Alpha 版、自定义主题与 CSS 注入、配置增强（Merge 和 Script）、系统代理守卫、TUN 模式、可视化节点/规则编辑、WebDav 备份同步。PRIVACY.md 声明不收集任何用户数据，配置与日志仅存本地。

代码型仓库之外，它同时是一个发行工程样板：多语言 README（docs/ 下 7 种语言）、14 种 UI 语言（src/locales/）、三平台矩阵构建 + 签名 + 自动更新，社区以 Telegram 频道与文档站（clash-verge-rev.github.io）运营。

## 5. 核心架构与关键实现

### 5.1 内核（mihomo）进程管理：Service/Sidecar 双模式

核心在 `src-tauri/src/core/manager/`（lifecycle.rs 1645 行、state.rs 704 行、mod.rs 366 行、config.rs 678 行）。CoreManager 以 `RunningMode { Service, Sidecar, NotRunning }` 区分内核运行方式，启动前先做纯函数决策：

```rust
// src-tauri/src/core/manager/lifecycle.rs
const fn startup_decision(status: &ServiceStatus, service_required: bool) -> StartupDecision {
    match status {
        ServiceStatus::Ready => StartupDecision::Service,
        ServiceStatus::NotInstalled if !service_required => StartupDecision::Sidecar,
        ServiceStatus::SidecarAllowed => StartupDecision::Sidecar,
        ServiceStatus::Checking | ServiceStatus::NotInstalled | ... => StartupDecision::Wait,
        ...
    }
}
```

`start_core_inner`（lifecycle.rs:610）按决策执行：Service 模式经 IPC 让特权服务拉起内核，Windows 上有 `run_service_start_with_sidecar_fallback` —— 服务启动失败且 Sidecar 可用时自动降级；Sidecar 模式则用 30 次 ×100ms 间隔、单次 400ms 超时的就绪探测等待内核 API 可用（state.rs 中 `SIDECAR_READINESS_*` 常量）。Windows 下 Sidecar 模式会在配置里强制关闭 TUN（`sidecar_config_without_tun`，state.rs），因为无提权无法创建虚拟网卡；GUI 升级为服务后由 `spawn_service_handoff_watcher` 交接。所有失败路径都有 `rollback_failed_start` 保证运行状态不残留"假运行"。

### 5.2 特权服务生命周期

`src-tauri/src/core/service.rs` 是全仓库最大文件（101KB）。服务状态被建模为显式状态机：`ServiceStatus::{Ready, NotInstalled, NeedsReinstall, InstallRequired, UninstallRequired, ReinstallRequired, ForceReinstallRequired, SidecarAllowed, Checking, Unavailable}`，未决动作（安装/卸载/重装）持久化后由 UI 引导执行；安装/卸载通过打包的 `clash-verge-service-install/uninstall` 工具完成（service.rs:603/724 附近）。IPC 层依赖独立仓库 clash-verge-service-ipc（src-tauri/Cargo.toml，tag v2.7.6），版本不匹配会进入 NeedsReinstall 流程。

### 5.3 系统代理接管与守卫

`src-tauri/src/core/sysopt.rs` + `proxy_control.rs`（合计约 85KB）封装 sysproxy crate。要点：

- 应用顺序感知 PAC 与全局代理的相互干扰：Windows 上关闭 PAC 会清掉 WinINET 代理标志，因此"开全局、关 PAC"时先清 PAC 再设代理（sysopt.rs `proxy_apply_steps` 注释与实现）。
- 写入失败后的状态推断：`authoritative_state_from` 区分 `Unchanged`（无写入落地）与 `Unknown`（部分写入），作为回滚与告警的依据，Linux 上 setter 成功不视为可靠写入证据（sysopt.rs）。
- 清除系统代理带固定次数重试，系统调用瞬时失败（RPC hiccup）不直接报错（proxy_control.rs `clear_with_retry`）。
- 双路由：macOS 上代理设置可交给服务执行（`ProxyBackendRoute::Service`），避免 GUI 降权后写不进网络偏好（proxy_control.rs `apply()`）。
- 守卫模式借助 sysproxy 的 `GuardMonitor` 持续校验系统代理未被第三方软件改写，超时 10 秒后状态标记未知（sysopt.rs `GUARD_DRAIN_TIMEOUT`）。

### 5.4 配置增强链（Merge/Script/可视化编辑）

`src-tauri/src/enhance/mod.rs`（1913 行）的 `enhance()` 是订阅到内核运行配置的完整流水线，顺序为：订阅 YAML → 可视化 rules/proxies/groups 增量（SeqMap）→ 合并 GUI 基础配置（端口/外部控制器/TUN 等）→ 内置脚本（builtin/meta_guard.js、meta_hy_alpn.js）→ TUN 覆盖 → DNS 设置 → 全局 Merge/Script → 订阅级 Merge/Script → 权威字段强制（`AuthoritativeFields` 保证 GUI 掌控的键不被用户脚本覆盖）→ 清理代理组与排序。

用户脚本在 Boa 引擎中沙箱执行，有明确资源上限（enhance/script.rs）：

```rust
const MAX_OUTPUT_SIZE: usize = 1024 * 1024; // 1MB
const MAX_JSON_SIZE: usize = 10 * 1024 * 1024; // 10MB
const MAX_LOOP_ITERATIONS: u64 = 10_000_000;
const SCRIPT_TIMEOUT: std::time::Duration = std::time::Duration::from_secs(5);
```

脚本永不使增强流程失败：异常被记录并原样返回输入配置（script.rs 注释 "Never fails"）。内核切换配置前还会经 `core/validate.rs` 校验，runtime_bundle.rs 负责把最终 YAML、GEO 资源（Country.mmdb、geosite.dat 等）与远程 provider 清单打包并做 SHA256/路径穿越校验后交给服务。

## 9. 亮点与风险

亮点：

1. Service/Sidecar 双运行模式 + 完整降级/交接链路（服务失败回退 Sidecar、macOS 代理设置交给服务、Windows Sidecar 自动禁 TUN），把桌面代理最难的权限问题做成了清晰状态机（src-tauri/src/core/manager/lifecycle.rs、service.rs）。
2. 用户脚本用内嵌 Boa 引擎沙箱执行，带超时/循环/输出三重上限且"永不失败"，兼顾灵活性与安全（src-tauri/src/enhance/script.rs）。
3. tauri-specta 契约生成 + contract-parity CI + check-architecture.mjs 架构门禁，前后端类型一致性有机制保障（src-tauri/src/ipc.rs、scripts/gen-contract.mjs）。
4. 工程纪律突出：60 余项 clippy deny、377 个 Rust 内联测试、cargo-deny/renovate/knip、21 条 CI 流水线，质量基建在同类开源 GUI 中属第一梯队。
5. 平台覆盖与本地化完整：三平台六架构、14 种 UI 语言（含 RTL 的阿拉伯语/波斯语）、7 语言 README。

风险/局限：

1. 供应链耦合：内核 mihomo、特权服务（clash-verge-service-ipc v2.7.6 固定 tag）均为外部仓库，任一上游变动或因合规原因下架都会直接影响可用性（Clash 生态 2023 年已有删库先例）。
2. 巨型文件：core/service.rs 101KB、enhance/mod.rs 1913 行、proxy_control.rs 47KB，虽有状态机建模但阅读与维护成本偏高。
3. README 混入机场与商业产品推广内容（README.md "Promotion" 章节），对工具中立性形象有折损，也存在推广资质不可核验的问题。
4. 代理工具的合规性因地区而异，GPL-3.0 与高曝光度使其持续处于监管关注风险中；贡献者约 185 人但核心维护者集中度"未确认"。

## 10. 总结评价

Clash Verge Rev 是"Go 内核 + Tauri 壳"路线里完成度最高的桌面代理客户端：它把特权服务、系统代理守卫、TUN 提权、配置增强沙箱这些容易被 GUI 项目做糙的部分，用显式状态机、内联测试与 CI 门禁做成了可审计的工程。代码质量基建（严格 clippy、契约生成、架构检查、AI PR 门禁）甚至超出多数基础设施项目的标准，适合作为 Tauri 大型应用的工程范本来读；对想理解系统代理/TUN 权限模型的开发者，core/manager 与 sysopt/proxy_control 两个模块尤其值得精读。使用者则应注意其供应链依赖与所在地区的合规边界。
