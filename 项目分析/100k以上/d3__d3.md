## 1. 项目速览

一句话定位：D3（Data-Driven Documents）是事实上的 Web 数据可视化标准库；本仓库（d3/d3）是 v7 时代的"伞形元包"——真正的算法实现拆分在 30 个独立的 d3-* 子模块仓库中，本仓库负责统一 re-export、打浏览器 bundle、托管官网 d3js.org。

## 2. 项目是什么，解决什么问题

D3 是一个免费开源的 JavaScript 数据可视化库，自述为"低层方法 + Web 标准（SVG/Canvas/CSS/HTML），提供无与伦比的灵活性来创作动态数据驱动图形"（`README.md`）。它不提供开箱即用的图表类型，而是提供把数据绑定到 DOM、再由比例尺/形状生成器/布局算法驱动渲染的原语，让作者完全掌控最终图形——这正是它十多年来支撑了大量获奖新闻可视化（NYT 图表组为代表）、并成为高层图表库（Plotly、Recharts、Observable Plot 等）底层基石的原因。

从 v4（2016 年）起，D3 的工程形态发生了决定性变化：单体仓库拆分为约 30 个独立发布到 npm 的模块（d3-array、d3-selection、d3-scale……），每个模块有自己的仓库、测试和版本节奏。本仓库自那以后就不再是"实现仓库"，而是一个组织壳（元包）：

1. **API 汇聚点**：`src/index.js` 全部 30 行就是 `export * from "d3-array"` 这样的 30 条 re-export，把所有子模块的公开 API 合成一个 `d3` 命名空间；
2. **浏览器分发点**：`bundle.js` + `rollup.config.js` 把 30 个模块 tree-shake-free 地打成 UMD（`dist/d3.js`）、ESM（`dist/d3.mjs`）和压缩版（`dist/d3.min.js`）三种产物，供 CDN（jsDelivr/unpkg，见 `package.json` 的 `jsdelivr`/`unpkg` 字段）直接引用；
3. **文档官网本体**：`docs/` 目录就是 d3js.org 的 VitePress 站点源码，包含全部 API 文档（116 个 md 文件）和数十个可交互的 Vue 示例组件。

因此评价 D3 的"核心实现"要看 30 个子仓库，但本仓库完整保留了 D3 的版本史（`CHANGES.md` 达 162KB，从 2.x 一直写到 7.0）、API 总索引（`docs/api.md`，111KB）和发布工程，是理解 D3 生态组织方式的最佳样本。

## 3. 技术栈与依赖

- **语言**：纯 JavaScript（ESM，`package.json` 的 `"type": "module"`），Node >= 12；文档站点用 Vue 3 单文件组件。
- **运行时依赖（30 个）**：全部是第一方 d3-* 模块（`package.json` dependencies 与 `src/index.js` 一一对应），按职能分组：
  - 数据处理：d3-array、d3-dsv、d3-fetch、d3-format、d3-random、d3-time、d3-time-format；
  - 视觉映射：d3-scale、d3-scale-chromatic、d3-interpolate、d3-color；
  - 图形生成：d3-shape、d3-path、d3-polygon、d3-geo、d3-contour、d3-delaunay、d3-quadtree、d3-hierarchy、d3-chord；
  - DOM 与交互：d3-selection、d3-axis、d3-transition、d3-brush、d3-drag、d3-zoom、d3-dispatch；
  - 动画：d3-ease、d3-timer、d3-force。
- **构建/开发依赖**：rollup 3 + @rollup/plugin-{json,node-resolve,terser}（打包）、mocha 10 + eslint 8（测试与 lint）、vitepress 1.x + @observablehq/{plot,runtime}（文档站）、topojson-client（文档示例数据）。见 `package.json` devDependencies。
- **零第三方运行时依赖**：除 d3-* 家族外不依赖任何外部库，这是 D3 "Web 标准"哲学的直接体现。

## 4. 目录结构与代码组织

| 目录/文件 | 职责 |
|---|---|
| `src/index.js` | 唯一"源码"：30 行 re-export，合成 d3 命名空间 |
| `bundle.js` | rollup 入口，附加导出 package.json 的 version |
| `rollup.config.js` | 三产物打包配置（UMD/ESM/min），从 LICENSE 提取版权 banner |
| `docs/` | d3js.org 官网源码：116 个 md 文档 + `components/` 下 21 个 Vue/JS 交互示例组件 + `.vitepress/` 站点配置与主题 |
| `test/` | 仅 2 个测试：导出完整性测试、文档链接死链测试 |
| `prebuild.sh` | 55KB 生成脚本：从 d3/d3.github.com 仓库拷贝历代版本 bundle 到 `docs/public/`，供文档"多版本示例"使用 |
| `CHANGES.md` | 162KB 大版本变更史（2.x → 7.0） |
| `img/` | 文档配图（axis/pack v3 vs v4 对比图等） |

组织方式评述：这是典型的 **metapackage/monorepo 外壳** 模式——"实现分散、入口集中、文档同仓"。GitHub 语言统计显示 Shell 属于统计假象（`prebuild.sh` 一份文件行数压过全部 JS）；仓库 `size` 约 58MB（gh api），大头其实是 `docs/public` 引用的历史构建物与图片。对比 v3 时代单仓 4000+ 文件的结构，v4 后每个算法模块独立演进，本仓库代码量极少但地位等同"发行版"。

## 5. 核心架构与关键实现

本仓库没有算法实现，其"核心实现"是三套工程机制，均值得细读：

**（1）命名空间聚合与零泄漏契约测试**（`src/index.js` + `test/d3-test.js`）。聚合本身平淡无奇，但配套测试把"伞包不得丢 API"变成了自动契约：逐个动态 import 全部 30 个依赖，断言每个导出（除 version）都能在本仓库命名空间中取到（`test/d3-test.js:10-18`）：

```js
for (const moduleName in packageData.dependencies) {
  it(`d3 exports everything from ${moduleName}`, async () => {
    const module = await import(moduleName);
    for (const propertyName in module) {
      if (propertyName !== "version") {
        assert(propertyName in d3, `${moduleName} exports ${propertyName}`);
      }
    }
  });
}
```

**（2）文档即测试**（`test/docs-test.js`）。爬取 `docs/` 全部 markdown，解析内部链接与锚点（含显式 `{#anchor}`），断言零死链（`test/docs-test.js:4-29`）。116 个文档页的内部交叉引用由 CI 兜底，这是文档站能长期保持高质量的低成本手段。

**（3）双仓联动的文档构建与发布流**（`.github/workflows/deploy.yml`、`package.json` scripts、`docs/.vitepress/config.ts`）。文档站通过 Vite alias 把 `d3` 指向本地构建产物 `dist/d3.mjs`（`config.ts:26-27`），使 `docs/components/*.vue` 中的示例直接跑在"当前 HEAD 打出的 bundle"上；deploy 工作流会额外 checkout `d3/d3.github.com` 仓库、执行 `prebuild.sh` 拷贝历代版本 JS，再 `upload-pages-artifact` 部署到 GitHub Pages。发布流程则是 Mike Bostock 风格的极简两行：`prepublishOnly: rm -rf dist && rollup -c`、`postpublish: git push && git push --tags`（`package.json:83-84`）。

对 D3 本体架构感兴趣者，可从 `docs/.vitepress/config.ts:46-270` 的侧边栏读到官方的模块分类学（Visualization / Animation / Interaction / Data 四大类），它就是 30 个子模块依赖关系的"人肉摘要"；各模块算法细节（如 d3-force 的 velocity Verlet 积分、d3-scale 的插值尺度）在各自子仓库，本仓库不承载（未在本仓库内确认）。

## 6. 构建与运行

来自 `package.json` scripts 与 CI（`.github/workflows/test.yml`），均可直接使用：

```bash
yarn --frozen-lockfile          # 安装依赖
yarn test                       # mocha 'test/**/*-test.js' && eslint src test
yarn prepublishOnly             # rm -rf dist && rollup -c  → dist/d3.js|d3.mjs|d3.min.js
yarn docs:dev                   # 需 --experimental-network-imports；本地起文档站
yarn docs:build                 # 先跑 ./prebuild.sh（需先 checkout d3/d3.github.com 到 build/）再 vitepress build
yarn docs:preview               # 预览构建出的文档站
```

使用方式（面向用户，`docs/getting-started.md`）：ESM+CDN（`<script type="module">` + jsDelivr 的 `dist/d3.min.js`）、UMD 全局 `d3`、或 `npm install d3` 后 `import * as d3 from "d3"`（默认解析到 `src/index.js`，见 `package.json` 的 `module`/`exports` 字段）。

## 7. 测试与工程质量

- **测试规模极小但定位独特**：本仓库仅 `test/d3-test.js`（导出完整性）与 `test/docs-test.js`（文档死链）两份 mocha 测试。真正的算法测试（数千用例）分布在 30 个子仓库各自维护，本仓库不做集成测试——这是"分散实现 + 伞包"模式下的合理分工。
- **CI**（`.github/workflows/test.yml`）：push/PR 到 main 触发，Node 20 + yarn frozen-lockfile，依次跑 eslint（带 `::add-matcher::` 把 lint 结果标注到 PR）、mocha、`prepublishOnly`（验证可打包）和 `docs:build`（验证文档可构建）——一次 CI 把"发布三件事"全部预演。
- **代码质量观察**：eslint 仅 `eslint:recommended`（`.eslintrc.json`），无 TypeScript、无类型约束；rollup 配置里显式忽略 CIRCULAR_DEPENDENCY 警告（`rollup.config.js:28-31`），侧面反映模块间存在循环依赖的历史包袱。terser 的 `mangle.reserved` 手工保留 `InternMap`/`InternSet` 类名（`rollup.config.js:56-61`），属于压缩器的必要补丁。

## 9. 亮点与风险

**亮点**

1. **教科书级的生态拆分**：30 个可独立使用、独立测试、独立版本化的模块 + 一个零成本聚合的伞包，`src/index.js` 30 行就是全部"源码"，用最小维护面换取最大组合自由（`src/index.js`、`package.json`）。
2. **契约化的完整性保障**：导出完整性测试（`test/d3-test.js`）与文档死链测试（`test/docs-test.js`）把最易腐化的两件事——API 聚合与文档链接——交给 CI，代价极低、收益极高。
3. **文档站与代码同仓同构建**：示例组件直接 import 本地 `dist/d3.mjs`（`docs/.vitepress/config.ts`），文档永远与 HEAD 代码一致，且发布即部署（deploy.yml）。
4. **十六年版本史完整可读**：`CHANGES.md` 逐大版本记录破坏性变更及理由，是研究 JavaScript 生态演进（UMD→ESM、d3.event 全局→事件直传、InternMap 引入等）的一手材料。
5. **零第三方运行时依赖**，浏览器兼容面与供应链风险都极小。

**风险/局限**

1. 本仓库不承载任何算法实现——想读懂 D3 内核必须跨到 30 个子仓库，单看本仓库会严重低估项目复杂度。
2. 学习曲线陡峭：低层原语定位意味着没有"一个 API 画一张图"的捷径（`docs/what-is-d3.md`、`README.md` 自述 low-level approach）。
3. 无 TypeScript 类型、无循环依赖治理（rollup 静默该警告，`rollup.config.js`），对大型工程集成时的类型体验依赖社区 `@types/d3`（本仓库内未见类型文件，未确认）。
4. 主版本 2021 年冻结（v7），新特性投入转移到 Observable Plot；重依赖 D3 新能力的团队需评估长期演进方向。
5. GitHub 主语言标为 Shell 的统计假象，自动化工具链按语言筛选时会漏掉它。

## 10. 总结评价

d3/d3 是"用组织方式赢得十年"的 rare sample：仓库本身几乎不写代码，却通过元包聚合、契约测试、文档同仓三件套，把 30 个独立模块拧成一个不可拆散的品牌与分发单元，同时把 113k 星、22.7k fork 的社区稳稳锚定在这一个入口上。它适合三类人：数据可视化作者（查 `docs/` 即查全 API）、前端工程研究者（学习模块化拆分与伞包发布模式的最佳案例）、可视化库作者（将其作为底层依赖或对标对象）。想读算法源码的人应顺藤摸瓜到 d3-scale、d3-force、d3-selection 等子仓库；本仓库则是理解 D3 生态如何被"管理"的第一站。
