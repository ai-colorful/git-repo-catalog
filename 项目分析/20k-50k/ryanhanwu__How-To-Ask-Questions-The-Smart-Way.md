## 2. 项目是什么，解决什么问题

这是 ESR（Eric S. Raymond）与 Rick Moen 的名文 "How To Ask Questions The Smart Way"（原文发布于 http://www.catb.org/~esr/faqs/smart-questions.html ，见 `src/README.md:13`）的中文译本仓库。原文面向黑客社区，回答一个长期困扰开源社区的问题：新手如何在邮件列表、IRC、论坛等免费技术渠道提出"值得被回答"的问题。文中系统讲述了提问前的自查清单（搜索旧帖、读手册、读 FAQ、试着自己验证，共 7 条，`src/README-zh_CN.md:100-109`）、如何选择提问渠道、如何写标题与描述症状、如何解读 RTFM/STFW 式回复、以及如何避免被归类为"失败者（loser/luser）"（`src/README.md:85`）。

文档的思想内核是"提问者的努力程度决定回答质量"：好问题是激励与厚礼，不劳而获的提问是对志愿者时间的掠夺。标志性桥段"好问题与蠢问题"给出 3 组同题对照问法（蠢问题 vs 聪明问题，`src/README-zh_CN.md:578-630`），其中第三例正是 ESR 本人在 LKML（Linux 内核邮件列表）提问的真实案例——文末明言"他建议我记下这件事，这直接导致了本指南的出现"（`src/README-zh_CN.md:629`），交代了原文成文由来。

仓库同时维护繁体（`src/README.md`，739 行）与简体（`src/README-zh_CN.md`，676 行）两个版本，二者章节结构完全一致（各 12 个正文 H2 章、26 个 H3 小节）。头部明确翻译谱系："本中文指南是基于原文 3.10 版以及 2010 年由 Gasolin 所翻译版本的最新翻译"（`src/README.md:17`），署名链为三代译者接力："Copyleft 2001 by D.H.Grand(nOBODY/Ginux), 2010 by Gasolin, 2015-present by Ryan Wu"（`src/README.md:15`）。

值得注意的是仓库自带"防误用"机制：开篇"声明"章要求任何链接本指南的项目在链接旁显著注明"本指南不提供此项目的实际支持服务！"，并直言曾因缺少该声明而"不停地被一些白痴纠缠"（`src/README.md:65-73`）——一份教人提问的文档，自己反而成了被错误求助的重灾区。

## 3. 技术栈与依赖

无任何运行时依赖与构建工具链，纯静态内容仓：

- **Markdown**：`README.md`（繁体，64025→74172 字节 739 行）、`README-zh_CN.md`（简体，64025 字节 676 行）为全部正文；繁体版实测 17756 个汉字，简体版 17737 个汉字。
- **GitBook 遗留配置**：`src/book.json`（仅 5 行，指定 `"readme": "README.md"` 为入口）、`src/SUMMARY.md`（仅 1 行 `# Summary` 占位）、`src/toc.js`（21 行浏览器端脚本，用 jQuery 扫描 `article :header` 生成锚点目录）——这是一套早已弃用的 GitBook 发布方案的残留，说明历史上曾尝试以电子书形式发布，现完全依赖 GitHub 渲染传播。
- **all-contributors 规范**：`src/.all-contributorsrc`（8831 字节）记录 35 位贡献者，贡献类型全部为 `translation`；README 尾部由 `<!-- ALL-CONTRIBUTORS-LIST -->` 注释块自动维护徽章与表格（`src/README.md:678-738`）。
- GitHub 元数据 `language: JavaScript`（因 toc.js 唯一"代码"文件），与内容型仓库实质不符，属平台标记偏差。

## 5. 核心架构与关键实现

内容型仓库无代码架构，以下为"内容结构"分析：

**章节骨架**（两版一致，出处 `src/README-zh_CN.md:22-60` 目录）：12 个正文章依次为 声明 → 简介 → 在提问之前 → 当你提问时 → 如何解读答案 → 如何避免扮演失败者 → 不该问的问题 → 好问题与蠢问题 → 如果得不到回答 → 如何更好地回答问题 → 相关资源 → 鸣谢。逻辑上是"提问前准备 → 提问现场技巧 → 解读回应 → 心态与礼仪 → 双向视角（如何回答）"的完整闭环。

**篇幅分布**："当你提问时"是绝对主体（简体 122-440 行，约 320 行，占全文 47%），下含 22 个 H3 小节，覆盖选论坛、写标题、描述症状、描述目标而非过程、去掉无意义问句、别写"紧急"、问题解决后追加说明等实操细则。"不该问的问题"（501-577 行）与"好问题与蠢问题"（578-630 行）合计约 130 行，是"劝退话术"与"示范模板"两大名场面。

**原文版本考证**（出处 `src/history.md`）：译文所据底本为 Revision 3.10（2014-05-21，esr，"新增 Stack Overflow 段落"），这也是原文迄今最后一个修订版。表内向上追溯：3.9/3.8 修 URL（2012/2013）、3.7 两次（2010，新增非英文母语者提示）、3.6/3.5（2008）、3.4（2007，新增"当询问有关代码的问题时"段落）、3.3（2006，加入 Rick Moen 内容）、3.2（2006）、3.1（2004）、3.0（2004-02-02 论坛礼仪大版本）。即译文自 2015 年重译以来，内容始终与 2014 年定稿的 3.10 版同步，不存在"落后于原文"的问题。

**翻译谱系考证**（出处 `src/README.md:15-17`、`src/README-zh_CN.md:12-14`）：2001 年 D.H.Grand(nOBODY/Ginux) 首译 → 2010 年 Gasolin 更新 → 2015 年起 Ryan Wu 接手并基于 3.10 版重译至今。GitHub 仓库创建于 2015-03-28（gh api），即第三代译本的载体；前两代译本流传于更早的中文 Linux 社区。

**差异管理**：繁/简版头部互链（`README.md:21` ↔ `README-zh_CN.md:18`），正文由不同译者/校对者分头维护，措辞有本地化差异（如繁版保留"駭客""魯蛇→loser"修正记录，见 2023-10-05 提交"将魯蛇改为loser"）。

## 6. 构建与运行

无可构建内容。使用方式即阅读与链接：

- 阅读：直接打开 `README.md`（繁体）或 `README-zh_CN.md`（简体），GitHub 自动渲染。
- 链接引用：按 `src/README.md:65-73` 声明章要求，链接处需注明"本指南不提供此项目的实际支持服务！"。

## 7. 内容质量与校对机制（内容型特例）

质量来自"三代译者 + 众包勘误"模式：主笔署名接力（D.H.Grand → Gasolin → Ryan Wu），35 位贡献者全部以 `translation` 类型记入 `src/.all-contributorsrc`，近期提交均为小幅译校（2024-04-14 "Remove unnecessary HTML tags"、2023-10-05 "修正翻译问题"、2023-10-05 "将魯蛇改为loser"）。校对靠社区 PR 驱动，无 CI、无 lint、无自动化检查（tarball 内 `.github/` 仅一个 issue 模板，无 workflows）。繁简双版本逐章对应、目录锚点互链完整，交叉引用（如正文 `STFW` 指回 RTFM 节，`src/README-zh_CN.md:587`）维护良好。没有发现明显的烂尾或断链段落。

## 8. 社区影响与文化地位（内容型特例）

- **传播规模**：约 39.5k 星、5818 fork（快照 + gh api 2026-11-17 实测），2015-03-28 创建（gh api）。它是中文技术圈引用密度最高的"提问礼仪"文本：大量开源项目 README、群规、新人引导文档直接链接此文，以至原文 ESR 官方页面收录的译本列表中此译本是最活跃的中文版之一（原文侧信息未在仓库文件中出现，未确认）。
- **"劝退文档"现象**：文中"失败者（luser）"称谓、RTFM/STFW 粗口缩写、"熬过去，这很正常"（`src/README.md:481-490` 附近）等段落，使其同时承担"新人守则"与"社区冷脸"两种角色——不少中文社区把链接此文作为回复低质量提问的标准动作，这既放大了传播，也放大了争议。
- **争议的客观陈述**：文档对"傲慢"指控有正面自辩："如果你厌恶我们的态度……我们并没有要求你向我们屈服"（`src/README.md:91`）；"如何避免扮演失败者"一章明确主张公开纠错优于私下委婉。该立场十余年来在中文社区持续引发"技术社区是否应如此敌视新手"的讨论，本文档本身不对此下判断，仅陈述其作为争议文本的地位。
- **维护节奏**：内容已随原文 3.10 版定稿而基本冻结，仓库呈"低频微调"状态——最近 push 为 2025-01-01（合并 PR 更新 LICENSE 年份，gh api commits），open issues 仅 12 个，issue 模板自带"劝退"过滤。对内容型文档而言，冻结即稳定，不算失修。

## 9. 亮点与风险

**亮点**

1. 翻译谱系清晰、底本明确：头部即声明依据原文 3.10 版（`src/README.md:17`），`history.md` 完整保留原文 12 次修订记录，可追溯性在翻译类仓库中罕见地好。
2. 繁/简双版本逐章同步，结构对齐（各 12 个 H2 章、26 个 H3 小节），覆盖两岸三地主要中文读者。
3. 自带防误用声明与"翻译本身"专用 issue 模板，把"被错误求助"和"跑题 Issue"两类噪音前置过滤（`src/README.md:65-73`、`src/.github/issue_template.md`）。
4. all-contributors 机制持续署名 35 位译者，社区参与感与勘误动力兼顾。
5. 极低维护成本：单 Markdown 主体即可承载近 4 万星传播，"内容即全部"的典范。

**风险/局限**

1. 许可关系存在结构性模糊：仓库层为 MIT（`src/LICENSE`），但译文头部仅标注"英文版版权归 ESR, Rick Moen 所有"（`src/README.md:11`），仓库文件内未见 CC BY-NC-ND 字样（grep 无命中）；ESR 原文官网实际采用 CC BY-NC-ND 授权之说未在仓库内体现，未确认。MIT 包装 + 归属声明的双层结构对下游再分发者不够直观。
2. 正文基本冻结于 2014 年的原文 3.10 版，技术语境已老化（IRC、邮件列表、新闻组权重远超当下；Stack Overflow 段落写于其鼎盛期），文档自身对此无时间戳提示。
3. 繁/简两文件手工双维护，长期存在漂移风险（2023-2025 年的修正多为单侧打补丁）。
4. GitBook 遗留文件（`book.json`/`SUMMARY.md`/`toc.js`）已成死配置，对新人构成轻微误导。

## 10. 总结评价

一个以近 4 万星证明"好文档自带传播力"的内容型仓库：它没有一行需要构建的代码，却完成了三代中文译者（2001/2010/2015 谱系清晰可考）对 ESR 原文 3.10 版的忠实传递，并借"好问题 vs 蠢问题"的对照范式与 RTFM/STFW 等符号化表达，深度嵌入中文技术社区的提问礼仪语境，成为引用最广、争议也最大的"劝退文档"。它适合两类读者：任何准备在开源社区提问的新人（无论是否接受其语气，提问自查清单部分是普适的），以及研究技术社区文化、文档传播与翻译接力模式的观察者。对想"读源码"的人，这个仓库能提供的只有极简内容仓的组织方式样本——而它恰恰说明，在 GitHub 上，结构与维护纪律比代码量更能决定一份文本能走多远。
