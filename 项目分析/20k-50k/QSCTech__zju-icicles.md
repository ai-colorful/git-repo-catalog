## 2. 项目是什么，解决什么问题

课程资料与"过来人经验"在大学里长期以 QQ 群文件、CC98 校园论坛帖子、学长学姐口口相传的方式碎片化流通：群文件缺乏组织、随年级解散而失传，论坛信息被时间淹没。`README.md` 前言对此有非常具体的痛点陈述——"某些重要信息的得到却往往依然是纯属偶然"，作者（求是潮技术团队）希望"将隐晦的、不确定的、口口相传的资料和经验，变为公开的、易于获取的、大家能够共同完善积累的共享资料"，理念是"只要是前人走过的弯路，后人就不必再走"。

选择 GitHub 作为平台是经过权衡的（`README.md` 第 30-36 行）：GitHub 支持目录组织且每个目录可同时显示文件列表与 README，天然适合"一课程一目录一攻略"的结构；Issue 和 PR 协作机制让贡献质量可监督。相比之下 QQ 群按年级/专业分割，无法长期共同维护。

收录内容包括：选课攻略、电子版教材、平时作业答案、历年试卷、复习资料、开卷考试 A4 纸等（`README.md` 第 17-28 行）。项目自述"已覆盖大多数计科的专业课程"，但从实际文件树看，现已远超计算机学院范围——覆盖了动物科学（兽医系列课程）、经济学、外语、体育、艺术等院系课程，实际是一个全校性的共享计划。

仓库名的 "icicles"（冰柱/冰凌）含义在 README 与仓库文件中均无解释，来源未确认。

## 3. 技术栈与依赖

这是一个内容型仓库，技术栈极薄，仅服务于"文档站自动生成"这一个工程目标：

- **Python 3**（标准库 `os` / `urllib.parse`）：唯一脚本 `update.py`（59 行），负责遍历课程目录生成 mkdocs 页面，无第三方依赖逻辑。
- **mkdocs**（`requirements.txt`，唯一运行依赖）：文档站生成器，主题为 readthedocs（`mkdocs.yml`：`site_name: 浙江大学课程攻略共享计划`、`theme: readthedocs`）。
- **开发依赖**：autopep8、pylint（`requirements-dev.txt`）。
- **CI**：GitHub Actions 单工作流 `.github/workflows/main.yml`。
- **Git LFS**：`.gitattributes` 含 `pack-*.pack filter=lfs ... -text` 配置，说明仓库历史上经历过大文件 LFS 迁移；这也是 codeload tarball 不适合获取本仓库的原因之一。

内容侧的"格式栈"由资料本身的形态决定：PDF 1,765 个占绝对主导（37.2%），其后为 Word 系列（docx 300 + doc 143 + xls 30 + xlsx 20）、PPT 系列（ppt 277 + pptx 129）、Markdown 315、图片（png/jpg/gif 共 362）；还夹杂少量课程遗留代码（C 228、汇编 42、C++ 34、Java 13、Scala 10、Python 31）与硬件实验产物（Xilinx ISE 工程文件 .tig/.xmsgs/.ncd/.ngd 等百余个，甚至有 19 个 .exe）。数据来源：Trees API 全量统计。

组织方式评述：这是"扁平化 + 约定优于治理"的结构。好处是贡献者零学习成本——网页端上传时把地址栏目录名改成课程名即可建新目录（`README.md` 第 60-66 行专门教这一招）；代价是 175 个顶层目录已显拥挤且无官方归类导航，课程间深度不均（最深 11 层：汇编与接口/首山雄(x86)/实验资料 下嵌套 500 个网页归档条目）。

## 5. 核心架构与关键实现

内容仓的"核心实现"有两块：目录约定本身，以及一条极简的自动化管线。

**（1）update.py —— 目录树到文档站的桥接器**（`update.py`）

脚本枚举顶层目录作为课程清单（排除 `.git`、`docs`、`.vscode`、`.circleci`、`site`），对每门课递归 os.walk 生成"文件列表"Markdown，并把课程自带的 README 内容拼在文件列表之前：

```python
def list_files(course: str):
    filelist_texts = '## 文件列表\n\n'
    for root, dirs, files in os.walk(course):
        for f in files:
            if f.split('.')[-1] in TXT_EXTS:
                filelist_texts += '- [{}]({})\n'.format(f, TXT_URL_PREFIX + quote(...))
            else:
                filelist_texts += '- [{}]({})\n'.format(f, BIN_URL_PREFIX + quote(...))
```

文本文件（md/txt）链接指向 GitHub blob 页、二进制指向 raw 地址（`TXT_URL_PREFIX`/`BIN_URL_PREFIX`，第 11-12 行）。这样每门课在文档站上都获得"攻略正文 + 可点击文件树"的一页，仓库的主 README 被复用为 `docs/index.md` 首页（第 57-61 行）。

**（2）CI 自动部署管线**（`.github/workflows/main.yml`）

单 job 工作流：push 到 master 触发 → setup-python 3.x → `pip install mkdocs` → 运行 `./update.py` 重新生成 docs → `mhausenblas/mkdocs-deploy-gh-pages@nomaterial` 部署到 gh-pages。任何一次资料上传（哪怕只是网页端传一个 PDF）都会自动刷新线上文档站，贡献者无需关心站点维护。值得注意的瑕疵：action 版本陈旧（checkout@v2、setup-python@v2），且部署 action 用的是第三方社区版本。

**（3）目录约定即架构**

真正承载设计的是那套课程目录规范：课程名做顶层目录、目录内按资料类型分二级、每目录配 README 写攻略。这套约定让 130 名互不相识的贡献者在 9 年里无冲突地各自"认领"目录写入，无需中央审核结构设计——约定替代了治理。

## 9. 亮点与风险

**亮点**：

1. 范式开创者：2016 年把"课程攻略"从 QQ 群文件搬进 Git 仓库，用目录 + 目录 README + PR 的组合解决了资料组织、长期存续与协作监督三件事，其命名（icicles）与结构被浙工大、哈工程等校直接复制。
2. 极低贡献门槛：网页端上传即 PR、目录名即课程名的约定，让完全不懂 git 的学生也能贡献——130 名贡献者、271 个 PR 是这一设计的直接结果。
3. 内容真伪与质量有天然保障：历年试卷、A4 纸、考试题型复盘都是学生亲历产物，教师评价缩写惯例规避了点名风险。
4. 自动化文档站：一条 59 行脚本 + 单 job CI 让每次上传自动刷新线上站点，维护成本几乎为零（`update.py`、`.github/workflows/main.yml`）。
5. 持续生命力：9 年维护历史，2 年前仍在扩科（兽医系列 2026-01 补充），当前仍在稳定获星。

**风险与局限**：

1. 版权合规是结构性风险（客观陈述）：仓库混合了学生原创内容与版权不明的第三方材料（历年试卷版权归学校/教师、教材类内容尤甚）。项目采取的是"声明式边界 + 事后删除"策略——`README.md` 第 75-83 行明令禁止上传盗版电子书/付费软件/教师主页内容，并提供侵权投诉邮箱 tech@zjuqsc.com 承诺彻底清除；实际执行亦有痕迹（2026-09-07 提交 "Delete 数值分析/资料/黄劲老师提纲.pdf"）。但禁止条款无法覆盖所有灰色地带，仓库仍托管大量来源复杂的试卷与资料，法律边界始终处于事实状态而非法律确认。
2. 许可证缺失：GitHub 检测 license 为 null，CC-BY-NC-SA 仅写在 README 正文中，对复用者的法律指引不够正式，也不利于下游同类仓直接继承内容。
3. 组织退化：175 个顶层目录无分类导航，README 的"覆盖计科课程"自述与现实覆盖面脱节，新访客难以快速定位非计算机课程。
4. 技术债轻微但可见：CI action 版本陈旧（checkout@v2）、第三方部署 action、LFS 迁移残留配置，5.8 GB 的体积也使 fork/clone 成本高企（README 自己承认"由于本项目体积很大"）。

## 10. 总结评价

zju-icicles 是一个用最朴素的 Git 能力（目录、README、PR）解决真实校园痛点的教科书级案例：没有代码架构，只有目录约定和 59 行脚本，却支撑起 175 门课、4745 份资料、130 位贡献者、9 年持续运转的共享体系，并以 41k 星成为中文高校课程共享仓矩阵中星数第二、资历最老的标杆。它证明了一件事——当痛点足够真实（信息孤岛化）且贡献门槛足够低（网页上传）时，一个内容仓可以靠"约定 + 自动化"而非"治理 + 审核"长期自运转。适合想为母校搭建同类共享计划的学生直接参考其目录约定与 README 范式（同时应把 LICENSE 正式化、把分类导航补上，并认真对待试卷类内容的版权边界）；对研究开源社区协作模式的人而言，它也是"低代码仓库即平台"的极佳观察样本。
