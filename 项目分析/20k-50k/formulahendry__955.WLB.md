## 2. 项目是什么，解决什么问题

955.WLB 的历史背景非常明确：2019 年 3 月 26 日，996icu/996.ICU 上线，以"工作 996，生病 ICU"的口号引爆全网对互联网公司加班文化的讨论（gh api：996.ICU 创建于 2019-03-26，现 277,229 星）。仅一天之后，即 2019 年 3 月 27 日，上海开发者 formulahendry（韩骏，Jun Han）创建 955.WLB，把同一议题的方向反过来——与其用黑名单曝光加班公司，不如用白名单汇总不加班的公司。README.md 第 5 行开宗明义："与 996.ICU 相呼应，955 公司白名单。旨在让更多的人逃离 996，加入 955 的行列。"

仓库对两个口号做了成对定义（README.md L13-15）：996.ICU 是"工作 996，生病 ICU"的问题曝光；955.WLB 是"工作 955，work–life balance（工作与生活的平衡）"的解决方案指引。换言之，996.ICU 回答"要逃离什么"，955.WLB 回答"可以去哪里"，两者构成同一运动的一体两面。

工作制的分级定义体系在 README 头部给出（README.md L7-11）：

| 术语 | 定义（README.md 原文转录） |
|---|---|
| 996 | 早 9 点到岗，工作到晚 9 点，每周 6 天 |
| 955 | 早 9 点到岗，工作到下午 5 点，每周 5 天 |
| 944 | 早 9 点到岗，工作到下午 4 点，每周 4 天 |

说明部分（L23-26）还引入了 965、10-6-5、10-7-5、975、985、945、10-5-5、11-6-5 等变体术语，用以描述不同公司之间的细微差异——例如 975 表示"9 点到 7 点、每周 5 天"，985 则进一步逼近 996。这些术语此后成为中文互联网讨论工作制的通用词汇。

名单本体是 README 中 86 个条目（README.md L31-116），每条格式为 `* 公司名 - 城市`，公司按英文名首字母排序（Afterpay → Zoom），城市可多个并用 `/` 分隔。少数条目带限定注记，如 `IBM (GBS除外) - 北京/上海`、`Morgan Stanley (IT) - 上海`，还有一条标注 `Red Hat - 北京/上海/深圳/西安/remote` 允许远程办公。名单以微软、谷歌、苹果、亚马逊等外企为主，兼有豆瓣、知乎、酷安、唯品会等国内公司。

作者在"说明"部分（README.md L19-27）主动列出了 5 条免责声明，直面此类众包清单的固有局限：

1. 不能保证所有部门都是 955/10-6-5/965/10-7-5 的水平；
2. 就算部门的平均水平是 955/10-6-5/965/10-7-5，也有可能部分时间要加班；
3. 名单中部分公司的部分部门可能有 975 甚至 985 的情况，不要以偏概全；
4. 名单中部分公司的部分甚至较多部门可能有 945、10-5-5 或 11-6-5 的情况，也一并收录；
5. 上海居多是因为作者身处上海、对上海情况相对了解，并非 955 公司大多在上海，欢迎投票扩充名单。

这份自我声明是理解该仓库数据性质的钥匙。

仓库还提供了两条衍生消费路径：微信小程序"955WLB"（README.md L118-122，对应独立仓库 formulahendry/weapp-955-wlb，本地 `images/weapp-qr.jpg` 为小程序码）和"955 内推"公众号"HJ说"（README.md L124-128，为作者个人品牌入口）。

## 3. 技术栈与依赖

本仓库没有任何代码、构建系统或运行时依赖，技术栈为空。全部内容为：

- Markdown × 2：`README.md`（中文，128 行，主文档）、`README_en_US.md`（英文镜像版，129 行）；

## 4. 目录结构与代码组织

仓库共 4 个文件（tarball 解压核实），目录结构如下：

| 路径 | 职责 |
|---|---|
| `README.md` | 中文主文档：工作制定义、5 条免责声明、86 家公司名单、小程序与内推入口 |
| `README_en_US.md` | 英文镜像版，结构与中文版逐条对应；差异点：姊妹链接写 1155.Life（中文版写 944.Life，L17） |
| `images/weapp-qr.jpg` | 微信小程序"955WLB"二维码图 |

组织方式为典型的"单文件清单"：README 即数据库，全部信息沉淀在一个 Markdown 文件中，没有独立的数据文件（JSON/CSV）、没有 schema、没有自动化脚本。代价是中英两个 README 需要人工同步（当前条目一致，但姊妹链接已出现漂移），且数据无法被程序化消费——若要复用数据，只能直接解析 `* 公司 - 城市` 格式的行。此外仓库未设置 CONTRIBUTING、CODE_OF_CONDUCT、CI 等常规工程配套，仅保留了一个 issue 模板。

## 5. 核心架构与关键实现（清单组织与分级定义体系）

**条目组织**：单一扁平列表，按公司英文名首字母严格排序（README.md L31-116，Afterpay → Zoom），不分类、不分组、不按行业或城市索引。"分级"只存在于工作制术语层面（996/955/944/965/975 等），而非名单的可见分组——名单本身不标注每家公司具体属于哪一档，只有"基本不属于 996、相对接近 955/965 水平"这一总括判断（L21）。

**条目规模统计**：86 家公司（`grep -c '^\* '` 于名单区段 L31-116 实测）；86 条共含 138 次城市标注（一家公司可多城并列）：上海 64、北京 32、深圳 10、杭州 7、苏州 6、南京 4、西安 3、香港/武汉/成都/合肥/厦门各 2、无锡/广州/大连/remote 各 1。上海占约 46%，与作者"身处上海"的自述吻合；北京次之，多为外企中国研发中心；国内互联网大厂中仅豆瓣、知乎、酷安、唯品会等少数入选。

**条目粒度与限定语法**：以公司为粒度而非部门，靠括号注记做范围限定（`IBM (GBS除外)`、`Morgan Stanley (IT)`）和多城市斜杠并列来表达内部差异。这种语法简单但无 schema，无法表达"某公司上海 955 而北京 975"这类城市间差异。典型条目形态（README.md 实录，仅作格式示例）：

```markdown
* Airbnb - 北京
* Bosch Group - 上海/苏州/无锡
* IBM (GBS除外) - 北京/上海
* Red Hat - 北京/上海/深圳/西安/remote
```

**收录机制（核心"实现"层）**：README L27 明确"欢迎童鞋们继续投票，我会根据投票情况，加入更多公司"——即社区提名 + 维护者裁决的人工制。操作路径有两条：直接提交 PR 或使用 issue 模板（`.github/ISSUE_TEMPLATE/propose.md`，标题前缀 `[Propose new company]`，要求注明工作地点与中文名）。从提交历史看，60 次提交基本是逐次"Add companies"式的小步更新（gh api commits：最后一条即 "Add 5 companies"），最终均由作者合入主 README。

**与 996.ICU 的对照关系**：996.ICU 以黑名单（996 公司榜单）+ 佐证材料（新闻报道、劳动法规）组织内容，体量大、结构复杂（官网、多语言、法律板块）；955.WLB 则是对偶的极简白名单——86 行列表即全部。两者同为 2019-03 讨论窗口的核心节点，但归属不同：996.ICU 属于 996icu 组织，955.WLB 及其系列（944.Life、1155.Life、weapp-955-wlb）由 formulahendry 个人维护，README 明示"相呼应"而非隶属关系（README.md L5；`gh api` 显示 944.Life/1155.Life 两仓返回完全相同数据，疑其一重定向至另一，归属未确认）。

## 7. 内容质量与数据准确性（测试与工程质量特例）

**准确性固有不可验证**：955 与否取决于部门、地区、时期三个变量，而名单粒度停留在公司级。作者在 README.md L19-27 主动列出 5 条免责，明确"不能保证完全准确性"。清单无数据来源标注、无核实流程、无条目时间戳——读者无法知道某家公司的信息采集于何时、依据是什么。这是此类匿名自报式众包清单的固有局限，本报告不对其真实性做任何背书或否定。

**双语同步漂移**：中文版与英文版 86 条目当前一致，但姊妹链接已分叉——中文版 L17 写 `944.Life`（工作 944，生活为先），英文版 L17 写 `1155.Life`（工作 11-5-5，生活为先），说明两个文件各自独立编辑、无自动同步机制。

**无任何质量工具**：仓库没有 CI、没有链接校验、没有数据 lint、没有贡献者协议（本地文件树核实：无 `.github/workflows` 目录，`.github` 下仅一个 issue 模板）。纯人工维护。

**停更导致的时效性问题**：最后提交为 2025-02-03 "Add 5 companies"（gh api），此后名单完全冻结。期间各公司的经营变化（并购重组、业务调整、加班制度变化）不会反映在名单中，201 个 open issue（多为提名与数据争议）停更后无人处理。名单应视为"截至 2025 年 2 月的社区投票快照"而非现状描述。

## 9. 亮点与风险

**亮点**：

1. **时机与定位精准**：996.ICU 黑名单运动的"白名单"对偶产品，命名语义自解释（955 + WLB），从创建到 36k+ 星仅靠一份 README，是"README 即产品"极简开源形态的代表案例（gh api created_at 与星数佐证）。
2. **克制而诚实的免责声明**：README L19-27 的 5 条说明直面数据局限（部门差异、975/985 混入、上海偏差），透明度高于一般众包清单。
3. **低摩擦的贡献与消费路径**：提名 issue 模板标准化贡献入口，网页/小程序/公众号三渠道覆盖不同场景，可 fork 性极强（1,740 fork）。
4. **定义体系的语言遗产**：996/955/965/975 等术语经该系列仓库（与 996.ICU 共同）推广，成为中文互联网讨论工作制的通用词汇。

**风险/局限**：

1. **准确性固有不可验证**：无来源、无核实、无时间戳，公司级条目掩盖部门/团队/时期差异（作者自认，README L19-27）；众包投票机制无法防刷票与主观偏差。
2. **停更失效**：2025-02 冻结后不再反映现实，名单逐年过时；201 个 open issue 无人处理，提名通道名存实亡。
3. **无许可证**：未附 LICENSE（gh api `license: null`），严格意义上他人不可复制再分发，1,740 个 fork 的二次整理处于授权模糊地带。
4. **单点维护与地理偏差**：数据更新依赖作者个人判断与所处城市（上海），无联合维护者、无地区分舵，覆盖天然不均衡。

## 10. 总结评价

955.WLB 是 996.ICU 运动的直接衍生品：一份用 86 行 Markdown 回应"哪些公司不加班"的社区白名单，其价值在 2019 年的加班文化讨论窗口内被最大化，此后作为静态参考清单被反复引用至今。它展示了一种零代码、零依赖、靠命名与时机积累声量的极简开源形态，也暴露了众包清单的典型天花板：数据不可验证、公司级粒度掩盖内部差异、单点维护、停更即失效。作为"互联网公司工作制众包数据如何组织"与"README 即产品"的案例，它比大多数同类清单更值得读——作者的免责声明部分尤其坦诚；而名单内容本身已冻结于 2025 年 2 月，只具历史参考价值。需要再次强调：本报告仅客观记录该清单的收录标准、组织机制与社区争议，不验证、不评判任何公司的实际工作制，也不构成任何就业建议。
