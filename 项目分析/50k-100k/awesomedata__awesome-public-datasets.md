## 2. 项目是什么，解决什么问题

数据科学项目的第一步永远是"去哪找数据"。公开数据散落在政府门户、学术机构、Zenodo、Hugging Face、Kaggle 等数百个站点，检索成本高且质量参差。本仓库把经过筛选的数据集按主题归档成单文件清单，让使用者按领域快速定位（`src/README.rst` 开头自述："a list of topic-centric public data sources in high quality"，多数免费、少量收费）。

项目由 Xiaming Chen 在上海交通大学 OMNILab 攻读博士期间孵化，OMNILab 现已并入 BaiYuLan 开放 AI 社区（`src/README.rst` 第 11-12 行）。它诞生于 2014 年 11 月，是 awesome 清单生态最早的一批成员之一，在 `sindresorhus/awesome` 主清单中被收录引流（`src/README.rst` 第 13 行）。

与本仓库大多数内容仓不同，它的 README 是**机器生成的产物**：仓库首页明确写着"automatically generated by apd-core, DO NOT modify this file directly"（`src/README.rst` 第 15-17 行）。真正的条目数据源、贡献入口和 CI 都在同组织的姊妹仓库 `awesomedata/apd-core`（API 实测其描述为 "Core meta for awesome-public-datasets. Contribute new data here!"，最近 push 2026-10-29）。因此本仓库实质上是一份"发布物"，而非编辑工作区。

收录范围横跨学术与产业：从 Government（政府开放数据 200 条）、Economics（125 条）这类公共数据大户，到 MachineLearning（36 条）、NaturalLanguage（43 条）这类 ML 研究基准，再到 ProstateCancer（13 条）这样的极细垂直。条目本身多为外部链接，仓库内几乎不托管数据。

## 3. 技术栈与依赖

作为内容型仓库，技术栈极轻，核心是"单源生成"流水线：

- **reStructuredText**：README.rst（2399 行、约 279KB）是唯一的内容载体，用 RST 的行内链接语法 `` `Title <url>`_ `` 表达条目（`src/README.rst` 全文）。
- **YAML**：每个数据集在上游 apd-core 仓库对应一个 `.yml` 元数据文件（README 中每个条目都带 `[Meta <.../core/<分类>/<名称>.yml>]` 链接，如第 33 行），承载标题、描述、URL、状态等字段。
- **生成器**：apd-core 中的工具读取 YAML 目录、渲染出本仓库的 README.rst（生成机制在 `src/README.rst` 第 15-17 行声明；生成器代码在 apd-core 仓库，本仓库内未包含，未逐一核验其实现）。
- **状态图标**：|OK_ICON|/|FIXME_ICON| 两个 SVG/PNG 资源由 apd-core 的 `deploy/` 目录提供（`src/README.rst` 第 21-22 行）。

无 package.json、无 requirements.txt、无任何构建脚本——本仓库内没有可运行的工程，全部机器位于姊妹仓库。

## 4. 目录结构与代码组织

| 路径 | 职责 |
|---|---|
| `src/README.rst` | 全部内容：约 1118 条数据集条目 + 34 个主题章节 + 互补清单与致谢（2399 行） |
| `src/LICENSE` | MIT 许可证文本 |
| `src/Datasets/titanic.csv.zip` | 仓库内唯一数据文件：Kaggle Titanic 入门数据集（60KB CSV，2014-11-21 打包），建库初期的演示遗留 |

组织方式评述：这是典型的"发布仓/内容仓分离"结构。本仓库只保留生成结果（README.rst）和一个历史遗留示例数据集，条目的增删改全部发生在 apd-core 的 `core/<分类>/*.yml`。这种设计让 1.2 万 fork 的贡献压力被分流到源仓库，同时保证发布格式稳定统一。分类体系为扁平单级主题（34 类），按字母排序，无嵌套——在千条规模下够用，但 Government 内部 200 条已是平铺极限。

## 5. 核心架构与关键实现

内容型仓库，以"条目模型与组织方式"代替代码模块分析：

**（1）条目原子结构**（示例取自 `src/README.rst` 第 33 行）：

```rst
* |OK_ICON| `Chinese Tea Dataset - A curated, open dataset of 100+
  Chinese teas covering type, origin, [...] <https://chinatea.house/dataset/>`_
  [`Meta <https://github.com/awesomedata/apd-core/tree/master/core//Agriculture/Chinese-Tea-Dataset.yml>`_]
```

每个条目 = 状态图标 + "标题 - 一句话描述" + 数据集外链 + 指向上游 YAML 的 Meta 链接。描述被截断为固定长度（`[...]`），完整描述须点进 Meta YAML 查看——这是发布层对源数据的有意降采样，保证 README 可扫读。

**（2）分类体系与条目分布**（`src/README.rst` 全文统计）：34 个主题分类合计 1118 个带状态条目，Top 分类为 Government 200、Economics 125、SocialSciences 64、Finance 53、Healthcare 49、Biology 49、Transportation 47、NaturalLanguage 43、GIS 40、ImageProcessing 38、MachineLearning 36。体量反映公共数据的真实供给：政府与经济统计类远超 ML 基准类。

**（3）数据源托管分布**（对外链域名统计，`src/README.rst`）：github.com 250、huggingface.co 37、doi.org 25、zenodo.org 19、kaggle.com 19、web.archive.org 13、dataverse.harvard.edu 7——一半以上条目指向机构/学术托管（DOI、Zenodo、Dataverse），说明收录基调偏学术与官方数据，而非博客凑数。

**（4）状态灯系统**（`src/README.rst` 第 21-25 行）：每条目带 OK（"I am well"）或 FIXME（"Please fix me"）图标，当前 1008 OK / 112 FIXME，约 10% 条目被标记待修。这是极轻量的健康度自检：发现死链或数据失效的维护者只需切换图标，问题肉眼可见且可被统计。

## 6. 构建与运行

本仓库无构建、无测试、无可运行程序。使用方式即"读"：

- 在线浏览 README（GitHub 渲染 RST 自带目录，`.. contents::` 指令生成 Table of Contents，`src/README.rst` 第 27 行）。
- 贡献新条目：到 `awesomedata/apd-core` 按 CONTRIBUTING.md 提交 YAML（`src/README.rst` 第 16-17 行指引）。
- 加入 Slack 社区 `awesomedataworld.slack.com` 获取更新（仓库 homepage 与 `src/README.rst` 第 18-19 行）。

## 7. 质量管控与更新机制（内容型特例：代替测试与工程质量）

- **更新机制**：PR 流 → apd-core 的 YAML 文件 → 上游 CI 再生成本 README。本仓库 master 的历史提交因此几乎全是机器提交（最近一次 push 2026-10-28 与 apd-core 的 2026-10-29 吻合，GitHub API）。无 CHANGELOG、无版本发布——清单类内容以"持续滚动"代替版本化。
- **质量控制证据**：OK/FIXME 双状态灯（`src/README.rst` 第 21-25 行）提供失效自标记；167 个 open issue（API）大多为链接失效与收录建议（issue 内容未逐一核验，未确认）。
- **质量观察**：新条目描述统一截断、统一带 Meta 溯源链接，格式一致性极好；但**条目质量方差在变大**——2026 年新增条目中出现明显由数据集作者自推的小站（如 MachineLearning 节的 BenchGecko、Evidaxis、videofreetier 等，`src/README.rst` 第 1602-1640 行；Agriculture 节的多个 2026 商业统计页，第 33-71 行），与早期 Zenodo/DOI 学术条目相比审核门槛似有松动（推断，未确认）。

## 9. 亮点与风险

**亮点**

1. 时间卡位与生态位极佳：2014 年建库、入列 sindresorhus/awesome（`src/README.rst` 第 13 行），是数据科学浪潮中最早被书签化的清单之一，网络效应滚了 12 年。
2. 内容/发布分离架构：YAML 单源（apd-core）→ 生成 RST，条目可溯源、格式可保证、贡献可流水线化——这是 awesome 清单中少见的工程化做法（`src/README.rst` 第 15-17 行 + 每条 Meta 链接）。
3. 规模与覆盖真实：1118 条、34 分类、指向 250+ 个不同域名，政府/经济/社科三条线占近 400 条，是名副其实的"公共数据地图"（`src/README.rst` 统计）。
4. 轻量健康度信号：OK/FIXME 状态灯让约 10% 失效风险可见、可修（`src/README.rst` 第 21-25 行）。

**风险/局限**

1. 链接腐烂是清单类仓库的宿命：112 个 FIXME 条目 + 167 个 open issue，外链域名中 web.archive.org 已出现 13 次（靠存档续命）（`src/README.rst` 统计）。
2. 收录门槛松动：近年自推式、SEO 型小站条目增多，部分描述明显营销化（MachineLearning/Agriculture 节 2026 年新增条目，`src/README.rst`），清单的"HQ"承诺面临稀释。
3. 单级扁平分类在 Government（200 条）内部已难扫读，且 README 无按许可证/规模/格式的元数据列，筛选能力弱于搜索引擎。
4. 仓库本体零代码零测试，全部价值系于上游 apd-core 与人工维护的连续性——单点依赖。

## 10. 总结评价

这是 awesome 生态里最"基础设施级"的清单之一：它不解决问题本身，而是压缩"找数据"这件事的搜索成本，并靠内容/发布分离的流水线（apd-core YAML → 生成 README）把 12 年的更新压力工程化地接了下来。星数之所以能到 8 万，与其说靠运营，不如说靠三点——入行极早（2014）、被 awesome 主清单持续引流、以及每个数据科学学习者都绕不开的刚需。今天它的边际价值在下降（链接在老、新条目质量在漂、语义搜索正在替代人工清单），但作为按主题浏览公共数据供给面的"地图"，它仍是最好的起点之一。适合数据分析/ML 初学者按领域扫一遍找练手与科研数据，也适合维护自有清单的人研究它的生成式维护架构；没有源码可读，值得读的是 apd-core 的 YAML 模型与生成流程。
